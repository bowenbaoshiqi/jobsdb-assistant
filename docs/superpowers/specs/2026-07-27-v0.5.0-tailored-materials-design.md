# v0.5.0 Tailored Materials Design

## 1. Goal

v0.5.0 turns first-level job selection into a durable, per-job material
workflow. For every selected JobsDB job, the system generates:

- one English tailored CV as a PDF;
- one English cover letter between 100 and 300 words;
- a concise CV change summary;
- advisory Reviewer and ATS findings;
- a factual-consistency result.

The user can preview every version, mark it approved or rejected, and create a
new immutable version with optional feedback. v0.5.0 never submits an
application.

## 2. Product Boundary

### Included

- Batch request from the selected jobs in the local Dashboard.
- One independent material task per job.
- CC/Codex Agent execution through durable Python checkpoints.
- Pinned AI Job Search application-material capability.
- English CV, PDF, and English cover letter generation.
- Advisory Reviewer and ATS results.
- Factual-consistency warnings.
- Read-only PDF and cover-letter preview.
- Approve, reject, and regenerate-with-optional-feedback actions.
- Immutable versions, hashes, provenance, and audit events.
- A stable `approved` state that a later execution release can consume.

### Excluded

- Clicking JobsDB Submit.
- Uploading a tailored CV into Quick Apply.
- Filling or attaching a cover letter in JobsDB.
- Opening an Apply job as part of material approval.
- Recording an application receipt.
- Automatic repeated generation until Reviewer or ATS passes.
- Scheduling, notifications, or a remote Dashboard.

The next release consumes only approved material versions and implements
automatic Quick Apply or manual Apply execution.

## 3. User Flow

### 3.1 Initial generation

```text
select one or more evaluated jobs
  -> click "为已选职位生成定制材料"
  -> Python creates one task per selected job
  -> each task waits for the active CC/Codex Agent
  -> Agent generates structured material output
  -> Python validates, renders PDF, hashes and stores the package
  -> Dashboard shows "待审核"
```

Selecting five jobs creates five independent tasks, five CV PDFs, and five
cover letters. JDs are never merged into one CV.

### 3.2 Review

Each job displays a `查看材料` action. The material detail view contains:

- embedded CV PDF;
- PDF download;
- cover-letter body, word count, and copy action;
- CV change summary;
- Reviewer suggestions;
- ATS suggestions;
- factual-consistency findings;
- material version and status;
- JD snapshot, profile, evaluation, adapter commit, and artifact hashes;
- version history.

### 3.3 Decision

From `待审核` or `待审核（疑似事实问题）`, the user can:

- `通过`: lock this version as the approved version for the job;
- `不通过`: retain it but mark it rejected;
- `重新生成`: retain it and create a new version using optional feedback.

When factual consistency reports a problem, `通过` is an explicit human
override. The audit event records that the warning was visible and overridden.

### 3.4 Regeneration

Regeneration opens a small optional feedback field. Examples:

- emphasize team leadership;
- reduce implementation detail;
- shorten the cover letter;
- improve executive communication positioning.

Submitting the action creates version `N + 1`. It never edits version `N`.
The latest version becomes the default view, while all historical versions
remain available.

## 4. Status Model

Material task status:

```text
waiting_for_agent
generating
generated
failed
```

Material version review status:

```text
pending_review
pending_review_with_fact_warning
approved
approved_with_fact_override
rejected
superseded
```

Rules:

- A task failure does not stop other jobs in the same batch.
- Reviewer or ATS findings never change `pending_review` into failure.
- Factual findings produce `pending_review_with_fact_warning`.
- Approving a clean package produces `approved`.
- Approving a package with factual warnings produces
  `approved_with_fact_override`.
- Regenerating marks the old pending version `superseded`; an already approved
  historical version remains approved in history but is no longer the latest
  approved version once the user approves a newer version.
- Exactly one current approved version may be selected for future execution per
  job.

## 5. Stable Python Orchestration

The Dashboard and Python application do not call an AI provider.

1. Dashboard requests material generation.
2. Python resolves selected jobs, current immutable JD snapshots, the active
   confirmed profile, current valid evaluations, and the source CV.
3. Python writes one structured task under `workspace/ai-tasks/`.
4. The current CC/Codex Agent loads the pinned material capability and task.
5. The Agent writes one structured result.
6. Python validates identity, provenance, required artifacts, and fact-check
   structure.
7. Python renders or validates the PDF, computes hashes, moves artifacts into
   the private material workspace, and records the immutable package.
8. Dashboard reads only the Python API and repository.

If no Agent session is active, tasks remain safely in `waiting_for_agent`.

## 6. ApplicationMaterialAdapter

The adapter follows the existing pinned-integration pattern and does not modify
the AI Job Search fork.

Task identity includes:

- task ID and material version;
- integration ID, pinned commit, and contract version;
- job ID, immutable snapshot ID, URL, title, company, and JD text;
- evaluation ID and native A-F result;
- profile ID, version, hash, and projected profile bundle;
- source CV path and hash;
- optional regeneration feedback;
- output language requirements:
  - CV: English;
  - cover letter: English;
  - change/check summaries consumed by the Chinese Dashboard: Simplified
    Chinese.

Result identity includes the same binding fields plus:

- structured tailored CV source;
- PDF artifact;
- cover-letter text;
- cover-letter word count;
- change summary;
- Reviewer findings;
- ATS findings;
- factual findings with cited source facts;
- engine and prompt provenance.

The adapter rejects mismatched job, snapshot, profile, evaluation, integration,
or version identity.

## 7. Material Generation Rules

- Claims may only come from the immutable candidate profile, projected source
  CV, and other explicitly allowed profile sources.
- Wording, ordering, emphasis, and summary positioning may change.
- Employers, dates, titles, education, certifications, skills, metrics, team
  sizes, and project outcomes may not be invented.
- The cover letter must be English and 100–300 words.
- Each generated CV must be a readable PDF.
- Reviewer and ATS outputs are advisory and always shown.
- A failed factual check does not delete artifacts. It creates a visible warning
  that requires rejection, regeneration, or explicit human override.

## 8. Persistence

### 8.1 SQLite

`material_tasks` stores:

- task ID and batch ID;
- job ID and snapshot ID;
- profile and evaluation identity;
- target version;
- status and failure message;
- optional regeneration feedback;
- created, started, and completed timestamps.

`material_packages` stores:

- package ID, job ID, and version;
- material task ID;
- immutable identity and provenance;
- private artifact paths and SHA-256 hashes;
- cover-letter word count;
- structured Reviewer, ATS, fact, and change-summary JSON;
- review status;
- created timestamp.

`material_review_events` stores:

- event ID and package ID;
- action: approve, reject, regenerate;
- optional feedback;
- whether a fact warning was overridden;
- timestamp.

Database constraints enforce unique `(job_id, version)` and prevent multiple
current approved packages for one job.

### 8.2 Private files

```text
workspace/materials/<job-id>/v<version>/
  cv.pdf
  cover-letter.txt
  material-result.json
  checks.json
  manifest.json
```

`workspace/` remains gitignored. The manifest contains hashes and provenance,
not credentials. No material or candidate data may be uploaded as a CI
artifact.

## 9. Dashboard

### 9.1 Batch controls

- Selected-count area shows `为已选职位生成定制材料`.
- The action is disabled when no jobs are selected.
- Submitting shows how many independent tasks were created.
- Material progress is manually refreshed, consistent with v0.4.

### 9.2 Job card

The disabled future action becomes:

- `等待 Agent`;
- `生成中`;
- `查看材料`;
- `生成失败`.

The existing default-CV Quick Apply and manual Apply controls remain unchanged.
They do not consume v0.5 materials.

### 9.3 Material detail page

The page is local-only and includes:

- version selector;
- status banner;
- PDF preview and download;
- cover-letter preview, word count, and copy action;
- change, Reviewer, ATS, and factual sections;
- provenance and hashes;
- approve, reject, and regenerate controls.

Approval controls require an explicit click. Regenerate accepts optional
feedback. No control submits a job.

## 10. API

```text
POST /api/material-batches
GET  /api/material-batches/{batch_id}
GET  /api/jobs/{job_id}/materials
GET  /api/jobs/{job_id}/materials/{version}
GET  /api/jobs/{job_id}/materials/{version}/cv.pdf
POST /api/jobs/{job_id}/materials/{version}/approve
POST /api/jobs/{job_id}/materials/{version}/reject
POST /api/jobs/{job_id}/materials/{version}/regenerate
```

All state-changing endpoints validate job/version identity. Artifact serving
resolves only paths owned by the package repository and must reject traversal
or arbitrary filesystem paths.

## 11. Failure Handling

- One job failure never stops the batch.
- Invalid Agent output is retained privately with a validation error.
- Missing or unreadable PDF marks the task failed.
- Cover-letter length outside 100–300 words is reported as a generation
  validation failure.
- Reviewer or ATS concerns remain advisory.
- Fact concerns remain reviewable warnings.
- A missing active profile, evaluation, or snapshot rejects task creation
  before any Agent work.
- Repeated clicks are idempotent and do not create duplicate versions.
- Regeneration failure leaves every previous version intact.

## 12. Privacy and Public Repository Rules

- Candidate data, JDs, outputs, PDFs, cover letters, reviews, feedback, and
  task payloads remain under ignored private paths.
- No browser profile, Cookie, credential, screenshot, or HTML dump is committed.
- Public tests use synthetic candidate and job data.
- Logs report IDs and status without printing full CV or cover-letter content.
- The privacy guard covers material-workspace paths and common artifact names.

## 13. Manual JobsDB Diagnostics

The five existing live diagnostic scripts move under
`tests/manual/jobsdb_live/` with a safety README.

- They are manual diagnostics, not CI tests.
- They use the real persistent browser profile.
- They may click Quick Apply and Continue but never final Submit.
- Their screenshots and HTML remain private under `data/`.
- Their project-root resolution is adapted only for the new location.

## 14. Testing

Strict RED-GREEN TDD applies to every production change.

Required test layers:

- domain status and package invariants;
- v0.5 forward SQLite migration;
- repository versioning and review audit events;
- adapter task/result identity and fact structures;
- checkpoint generation, submission, and resume;
- batch isolation and idempotency;
- artifact hashing and safe path resolution;
- PDF and cover-letter validation;
- Dashboard API and state transitions;
- browser test for batch generation, preview, approve, reject, and regenerate;
- privacy and CI contracts;
- manual diagnostic scripts excluded from pytest collection.

New or materially changed Python modules target at least 90% branch coverage.
The full deterministic suite remains above the repository 80% release gate.

## 15. Release Completion

v0.5.0 is complete when:

- five selected jobs produce five independent durable tasks;
- the Agent can generate and submit material results through the Python
  workflow;
- every successful job has an English CV PDF and 100–300-word English cover
  letter;
- every package is immutable, hashed, and bound to its JD, profile, evaluation,
  adapter commit, and version;
- Reviewer and ATS suggestions are visible but non-blocking;
- factual warnings are visible and can be rejected, regenerated, or explicitly
  overridden;
- approve, reject, and regenerate create durable audit events;
- historical versions remain viewable;
- approved material is clearly marked ready for the next execution release;
- no v0.5 action submits an application;
- full tests, coverage, lint, privacy guard, documentation, changelog, and
  version checks pass.
