# v0.6.0 Closed-Loop Applications Design

**Date:** 2026-07-28  
**Status:** Approved in conversation; awaiting written-spec review  
**Release:** `0.6.0`

## 1. Outcome

v0.6 closes the product loop:

1. discover and score JobsDB roles;
2. select roles in the local Dashboard;
3. generate one immutable English application package per role;
4. review, reject, override, or regenerate each package;
5. prepare and submit approved Quick Apply applications;
6. hand off Apply roles for manual submission;
7. preserve a durable audit trail from JD snapshot to application result.

The foreground JobsDB Assistant worker is started once from CC or Codex and
remains active until the requested work finishes. Dashboard actions do not
require the user to return to the Agent session after every selection.

## 2. Scope

### 2.1 Included

- Use Bowen Bao resume v5 as the only v0.6 source template.
- Tailor only:
  - `Professional Summary`;
  - `Career Highlights`;
  - `Core Competencies`.
- Freeze `Work Experience` and every section after it.
- Generate a 100-300 word English cover letter for every selected role.
- Run advisory Reviewer and ATS checks.
- Run blocking factual-consistency and layout-integrity checks.
- Support review, rejection, explicit override, and regeneration.
- Process Dashboard work with one persistent foreground worker.
- Upload the approved tailored resume to JobsDB.
- Include the approved cover letter in every Quick Apply application.
- Pause for human handling instead of submitting incomplete materials.
- Open Apply roles for manual application with material download and copying.
- Record immutable application provenance and outcomes.

### 2.2 Excluded

- Changing work experience, education, certification, publications, or any
  section after `Core Competencies`.
- Multiple resume templates in v0.6.
- Automatically applying on external employer sites.
- Cloud hosting, background scheduling, or multi-user SaaS operation.
- Parallel browser applications.
- Tracking later JD changes.
- Automatically refreshing the Dashboard.

v0.7 may productize the v5 layout as a built-in template for other users.
Until then, the uploaded source resume must have the same structure as v5.

## 3. Architectural Principles

### 3.1 Python owns the workflow

Python and SQLite are the source of truth for tasks, versions, review state,
application state, idempotency, and recovery. The Agent supplies AI judgment
and structured text at explicit checkpoints. Browser application execution
remains deterministic Python code.

### 3.2 Forks remain unchanged and pinned

The project continues to consume the pinned AI Job Search capability for
material generation and the pinned Career Ops capability for evaluation.
Neither fork is edited. The JobsDB Assistant adapters define stable contracts
around their outputs.

### 3.3 One role, one immutable package

Every material package is bound to one:

- JobsDB job ID and JD snapshot hash;
- confirmed profile version and hash;
- Career Ops evaluation ID;
- material version;
- resume SHA256;
- cover-letter SHA256.

Regeneration creates a new version and never mutates an installed package.
Only the currently approved version is eligible for application.

## 4. Resume Template Contract

### 4.1 v5 geometry

The v5 resume is a two-page A4 PDF. On page one, `Work Experience` begins at
approximately `y=492pt`. All tailored regions are above this boundary. Page two
contains only frozen content.

The renderer uses named, fixed-height regions:

1. `Professional Summary`;
2. `Career Highlights`, fixed at four bullets;
3. `Core Competencies`, fixed at three groups.

Each region has fixed:

- coordinates;
- width and height;
- font family and size;
- line height;
- indentation and bullet style;
- maximum line count.

Content may use less than the available height. The renderer must not reduce
font size, line spacing, or margins to fit extra text.

### 4.2 Local redraw with frozen PDF content

The system preserves the v5 header, visual styling, frozen page-one region, and
the complete second page. It clears and redraws only the three allowed content
regions. AI output is structured text, not a complete PDF.

The renderer performs deterministic font-metric line wrapping. If content does
not fit, it returns a structured overflow result to the worker. The Agent then
compresses only the overflowing allowed region. A bounded number of correction
attempts is permitted; exhaustion fails material generation.

### 4.3 Blocking layout validation

Before a generated PDF can enter review, the validator confirms:

- the PDF has exactly two pages;
- all three tailored regions fit without clipping or overlap;
- configured font sizes and line heights were used;
- the `Work Experience` heading and content after it are textually identical
  to the source;
- frozen page-one text coordinates match within PDF floating-point tolerance;
- page two text and coordinates match the source;
- the output is no larger than 5 MB;
- text extraction remains usable for ATS processing;
- the file opens and renders without malformed PDF objects.

A frozen-region or layout failure is blocking and cannot be converted into a
normal review warning. The user may override a factual-risk review, but cannot
override a corrupted or structurally invalid PDF.

## 5. Material Generation

### 5.1 Input

Each generation task contains:

- v5 source resume path and SHA256;
- confirmed candidate profile and projected Career Ops bundle;
- current JobsDB JD snapshot;
- Career Ops evaluation;
- target material version;
- previous-version feedback for regeneration.

### 5.2 Structured AI output

The Agent returns:

- one Professional Summary;
- exactly four Career Highlights;
- exactly three Core Competency groups;
- one English cover letter of 100-300 words;
- change summary;
- Reviewer, ATS, and factual-consistency results;
- engine and prompt provenance.

The output contract has no fields for Work Experience or subsequent sections,
so those sections cannot be changed through the adapter.

### 5.3 Review semantics

- Reviewer and ATS results are advisory.
- Suspected fabricated or unsupported claims set a blocking factual-risk state.
- The user can explicitly override factual risk; the override stores actor,
  time, reason, material version, and hashes.
- Layout-integrity failure cannot be overridden.
- Rejection preserves the package.
- Regeneration creates a new immutable material version.

## 6. Foreground Worker

The worker is launched once by the JobsDB Assistant skill and services tasks
until the requested run is complete. It polls durable SQLite state with bounded
backoff and processes:

- pending material generation;
- material regeneration;
- Quick Apply preparation;
- Quick Apply continuation after confirmation or human handling;
- Apply manual handoff.

The worker emits durable progress events consumed by manual Dashboard refresh.
Only one browser application task can run at a time. Material generation may be
prepared independently, but installed packages and application state remain
transactional per job.

Stopping the worker is safe. Restarting it resumes from the last durable state
instead of duplicating a package or application.

## 7. Quick Apply Design

### 7.1 Remote single-resume strategy

JobsDB permits up to ten stored resumes and accepts PDF files up to 5 MB. The
user authorizes the assistant to delete every resume currently stored in the
selected JobsDB account, including the default resume.

For each queued Quick Apply role, serially:

1. lock the approved package and application task;
2. validate local files and hashes;
3. navigate to the selected account's JobsDB resume-management page;
4. delete every remote resume;
5. re-read the page and confirm that the remote list is empty;
6. upload the approved PDF using
   `JBA_<job-id>_v<version>_<hash-prefix>.pdf`;
7. re-read the list and confirm that exactly one resume exists with the exact
   expected filename;
8. open the bound JobsDB job ID;
9. enter Quick Apply;
10. select the unique tailored resume;
11. choose to include a cover letter and enter the approved text;
12. reach Review and verify the job ID, resume filename, and cover letter;
13. wait for user confirmation;
14. submit and verify the success state;
15. store the result and proceed to the next queued role.

The system does not delete local source resumes, generated packages, or
application history.

### 7.2 No incomplete fallback

Every Quick Apply must contain both the approved resume and approved cover
letter. Failure to locate, populate, or verify either item moves the task to
`waiting_for_human`. The system must not fall back to the JobsDB default resume
or to `Don't include a cover letter`.

### 7.3 Submission confirmation

Dashboard exposes separate actions:

- **Prepare application**: performs remote cleanup and upload, completes the
  application wizard, and stops at Review.
- **Confirm submission**: authorizes the irreversible Submit action.

The foreground worker remains active while waiting, so the user does not need
to return to CC or Codex.

## 8. Apply Manual Handoff

Apply roles do not automate external employer sites. The Dashboard action:

- opens the JobsDB detail page;
- displays and downloads the approved tailored resume;
- provides one-click cover-letter copying;
- records `manual_handoff`.

The product does not claim that the role was submitted. A later version may
allow the user to manually record an external result, but that is not required
for v0.6.

## 9. State Model

### 9.1 Material states

- `waiting_for_generation`
- `generating`
- `validation_failed`
- `waiting_for_review`
- `approved`
- `rejected`
- `regeneration_requested`

### 9.2 Application states

- `queued`
- `preparing_resume`
- `waiting_for_confirmation`
- `submitting`
- `waiting_for_human`
- `submission_uncertain`
- `submitted`
- `failed`
- `manual_handoff`

Each transition is persisted before the next external action. State-changing
commands use stable idempotency keys derived from the application identity.

## 10. Recovery and Error Handling

- **Interrupted after remote deletion:** restart preparation and upload again.
- **Interrupted after upload but before Review:** verify the sole remote resume
  against the expected filename before continuing.
- **CAPTCHA or expired login:** retain browser and task context in
  `waiting_for_human`; resume only after a new verification pass.
- **Unknown selector or changed page:** capture screenshot, URL, and current
  step; do not guess or click Submit.
- **Submit clicked but success not confirmed:** use `submission_uncertain` and
  require manual inspection; never automatically retry.
- **Existing submitted record for the job:** reject duplicate submission by
  default.
- **File or hash mismatch:** fail before browser submission.

## 11. Dashboard

The Simplified Chinese Dashboard adds:

- worker/task status with manual refresh;
- layout-integrity result;
- immutable material version and hashes;
- prepare-application action for approved Quick Apply roles;
- explicit final-submit confirmation;
- waiting-for-human instructions and resume action;
- manual handoff controls for Apply roles;
- application history and failure reason.

The existing direct default-CV/no-cover-letter shortcut remains available but
is not used by the approved-material workflow. Its label must make the
different behavior unmistakable.

## 12. Privacy and Audit

- Resume, profile, browser, checkpoint, and application data remain under
  gitignored private directories.
- No credentials or personal artifacts enter the repository.
- Logs use job ID, package ID, hashes, and safe filenames instead of resume
  contents or credentials.
- Every application record preserves job snapshot, profile version,
  evaluation ID, package version, material hashes, account alias, apply type,
  timestamps, transitions, and final outcome.

## 13. TDD and Acceptance

Development proceeds in three internal milestones:

1. v5 template rendering and frozen-region validation;
2. foreground worker and Dashboard task lifecycle;
3. remote resume replacement, Quick Apply, and Apply handoff.

Automated tests cover:

- fixed-height region wrapping and overflow;
- four-highlight and three-competency cardinality;
- frozen text and coordinate integrity;
- page-two integrity and two-page output;
- PDF size and ATS extraction;
- facts, override, rejection, regeneration, and version history;
- worker restart and idempotency;
- remote delete-all, empty-list confirmation, upload, and exact filename;
- job ID, material version, and hash binding;
- mandatory cover letter and Review verification;
- final confirmation boundary;
- CAPTCHA, expired login, selector changes, and uncertain submission;
- duplicate-application prevention;
- serial multi-job execution;
- Apply manual handoff;
- Simplified Chinese Dashboard states.

Manual acceptance uses at least two tailored jobs and verifies:

1. different allowed sections with identical frozen content;
2. rejection and regeneration;
3. one Quick Apply stopped safely at Review;
4. one confirmed real Quick Apply submission;
5. replacement of the first remote resume for the second job;
6. one Apply manual handoff;
7. worker stop and restart recovery.

The release is complete only when non-E2E tests, Dashboard browser tests,
privacy checks, PDF visual inspection, and the agreed live JobsDB checks pass.
