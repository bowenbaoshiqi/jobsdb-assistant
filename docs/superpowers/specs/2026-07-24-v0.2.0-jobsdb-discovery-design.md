# v0.2.0 JobsDB Discovery Design

**Date:** 2026-07-24

**Status:** Proposed for review

**Release:** `v0.2.0` — JobsDB Discovery

## 1. Outcome

Add keyword-based JobsDB HK discovery with the smallest safe change to the existing
auto-apply codebase.

A user supplies exactly one keyword. The assistant searches JobsDB Hong Kong, collects at
most 50 unique jobs, visits each job detail page, stores the complete JD, classifies its
application type, and records immutable content snapshots. Discovery does not score jobs,
generate application materials, render the Dashboard, or submit applications.

Example:

```bash
jobsdb-assistant discover --keyword "Product Manager"
```

## 2. Confirmed Product Decisions

- One keyword per discovery run.
- Hong Kong is the fixed default location for v0.2.
- JobsDB defaults are used for date, work type, sort order, and other filters.
- A run collects at most 50 unique JobsDB job IDs.
- Repeated jobs are deduplicated by JobsDB job ID.
- An unchanged JD reuses the current snapshot.
- A changed JD creates a new immutable snapshot.
- Previously submitted jobs remain discoverable but cannot be submitted twice.
- Apply types are `quick_apply`, `apply`, and `unknown`.
- The implementation extends the existing scraper instead of introducing a general
  multi-source discovery framework.

## 3. Scope

### Included

- `discover` CLI command with required `--keyword`;
- deterministic JobsDB HK search URL construction;
- reuse of the current browser, login session, and `HomepageScraper`;
- bounded lazy-load scrolling with no-growth termination;
- extraction and normalization of up to 50 unique job listings;
- detail-page navigation and complete JD extraction;
- apply-type classification;
- transactional job and snapshot persistence;
- incremental discovery summaries;
- protection against duplicate application for the active account;
- unit, integration, migration, and browser-contract tests.

### Excluded

- multiple keywords in one run;
- user-facing location and search-filter options;
- arbitrary search URL input;
- candidate onboarding and job scoring;
- CV or cover-letter generation;
- Dashboard and approval workflow;
- scheduled or unattended execution;
- automatic application from the `discover` command.

## 4. Minimal-Change Architecture

The existing orchestration and browser abstractions remain in place:

```text
discover --keyword
        |
        v
JobsDB search URL builder (new pure function)
        |
        v
existing PageController + login/profile
        |
        v
existing HomepageScraper (extended)
  - extract visible cards
  - scroll while the unique-ID count grows
  - stop at 50 or after bounded no-growth rounds
        |
        v
existing JobDetailPage (extended)
  - extract normalized full JD
  - classify apply type
        |
        v
Database + migration (extended)
  - job current state
  - immutable job snapshots
  - discovery run result
```

No new service or adapter process is introduced. `HomepageScraper` keeps its current name in
v0.2 to avoid a rename-only refactor. Its current recommendation-card extraction remains as
a compatibility fallback, while search-result selectors become the primary path during a
discovery run.

The existing `start` command and Quick Apply state machine keep their current behavior.

## 5. Search Input and URL Construction

`discover` rejects an empty or whitespace-only keyword. The normalized keyword preserves the
user's words while collapsing surrounding/repeated whitespace.

A small pure URL-builder function converts that value into the current canonical JobsDB HK
search form. URL encoding is performed by the standard library; keywords are never
interpolated into JavaScript or shell commands.

The URL builder owns JobsDB URL syntax so a future site change is isolated to one module.
Its output is covered by unit tests and one optional live browser contract test.

## 6. Listing Collection

The current scraper already scrolls, extracts `/job/{id}` links, and deduplicates IDs. v0.2
connects those capabilities into a bounded collection loop:

1. Wait for the initial result cards.
2. Extract all visible jobs.
3. Normalize canonical URLs and merge by JobsDB job ID.
4. Stop when 50 unique jobs have been collected.
5. Otherwise scroll to the bottom and wait for lazy-loaded results.
6. Repeat until the result count stops growing for a small bounded number of rounds.
7. If the live page exposes an explicit next-page control, use it only after scrolling has
   stopped producing results, then continue the same loop.

All round counts and waits are bounded. A sparse search may legitimately return fewer than
50 jobs and is still a successful run.

Extraction order is preserved so the first 50 unique jobs follow JobsDB's default ordering.
Deduplication occurs before applying the limit.

## 7. Detail Collection and Apply-Type Classification

For each listing, `JobDetailPage` navigates to its canonical detail URL and extracts:

- JobsDB job ID and canonical URL;
- title;
- company;
- location when available;
- the complete visible JD text;
- apply type.

JD normalization standardizes line endings, trims leading/trailing whitespace, and collapses
excess blank lines. It does not summarize, translate, or otherwise rewrite content.

Apply type is determined from the current detail page:

- `quick_apply`: a JobsDB Quick Apply control is present;
- `apply`: an Apply control is present and Quick Apply is absent;
- `unknown`: neither classification can be made reliably.

Quick Apply wins if contradictory controls are visible. Classification during discovery is
informational; the execution flow must re-check the page before a future application.

One failed detail page does not discard other collected jobs. The job is recorded with a
structured failure in the run summary, and no empty snapshot is created.

## 8. Persistence and Incremental Behavior

The v0.1 domain contracts remain authoritative. A new migration extends persistence for:

- current job metadata, apply type, first-seen and last-seen timestamps;
- immutable JD snapshots with SHA-256 content hashes and capture timestamps;
- the job's current snapshot reference;
- discovery runs and per-job outcomes sufficient for resumable reporting.

Persistence rules:

- **New job:** insert the job and its first snapshot.
- **Known job, unchanged normalized JD hash:** update `last_seen`; reuse the snapshot.
- **Known job, changed hash:** insert a new snapshot and point the job to it.
- **Known job with metadata/apply-type change only:** update current metadata without creating
  a duplicate JD snapshot.
- **Failed detail extraction:** record the failure; preserve the last valid job and snapshot.

Absence from the first 50 search results does not expire a job because ranking can change.
A job becomes inactive only when its detail page explicitly reports that it is closed,
expired, or unavailable. Historical snapshots are never overwritten or deleted.

Duplicate-application protection continues to use persisted application records for the
active account. Discovery may display an already-submitted job, but future queue creation
must reject it.

## 9. CLI Behavior

```bash
jobsdb-assistant discover --keyword "Product Manager"
```

The command opens the configured persistent browser profile and uses the existing login
handling. It performs discovery only and prints a final summary containing:

- requested keyword;
- unique listings found;
- detail pages successfully captured;
- new, unchanged, and changed jobs;
- Quick Apply, Apply, and unknown counts;
- failed detail captures with safe reason codes.

The command exits non-zero for invalid input, login failure, navigation failure before any
listing can be collected, or persistence failure. Individual detail failures produce a
partial-success summary and do not fail the entire run when at least one job is persisted.
No credentials, private profile paths, raw cookies, or full JD text are printed.

## 10. Error Handling and Safety

- Search navigation and bounded loading failures use the existing retry categories.
- Selector failures produce artifacts only under ignored `data/` paths.
- Database changes for one job and its snapshot are transactional.
- Existing user data is migrated forward; no table or column is destructively replaced.
- Search input is URL-encoded and safe for logs.
- The public-repository privacy checks from v0.1 remain mandatory.
- `discover` never calls the application state machine.

## 11. Testing Strategy

Development follows TDD.

### Unit tests

- keyword validation, normalization, and URL construction;
- listing extraction for recommendation and search-result fixtures;
- unique-ID limit and stable ordering;
- bounded scroll/no-growth termination;
- JD normalization and hashing;
- Quick Apply/Apply/unknown classification;
- incremental persistence result states.

### Integration tests

- migration from the v0.1 database;
- new, unchanged, changed, and failed-detail discovery cases;
- transactional snapshot/current-pointer updates;
- duplicate-application protection per account;
- CLI result and exit-code behavior.

### Browser-contract tests

- optional, explicitly selected test against the current JobsDB HK search page;
- verifies that at least one `/job/{id}` listing can be collected;
- verifies detail extraction and apply-type classification without submitting;
- never runs in default CI and never requires stored public credentials.

Default tests use `FakePageController` and do not launch a browser. The repository keeps at
least 80% line-and-branch coverage, and all privacy, lint, and existing regression checks
must remain green.

## 12. Compatibility and Completion Criteria

v0.2 is complete when:

- one keyword discovers up to 50 unique Hong Kong JobsDB jobs;
- bounded loading reuses the existing scraper and stops safely on sparse results;
- each successful detail capture stores a complete normalized JD and apply type;
- unchanged JDs do not create duplicate snapshots;
- changed JDs create immutable snapshots;
- explicit closed/expired detail pages mark jobs inactive;
- submitted jobs remain protected from duplicate application;
- `start` and the existing Quick Apply tests behave unchanged;
- migrations work from a real v0.1 schema;
- default tests, lint, privacy checks, and coverage gates pass.
