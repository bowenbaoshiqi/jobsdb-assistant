# v0.3.0 Candidate & Evaluation Design

**Status:** Draft for user review  
**Date:** 2026-07-24  
**Release:** `v0.3.0` — Candidate & Evaluation

## 1. Outcome

`v0.3.0` adds two capabilities to `jobsdb-assistant`:

1. a confirmed, versioned candidate profile produced with the relevant native
   `ai-job-search` onboarding capability; and
2. incremental JobsDB job evaluation using the native `career-ops` scoring method.

The Python application remains the workflow controller and SQLite remains the system of
record. Claude Code or Codex supplies AI reasoning only at explicit, schema-bound
checkpoints. The agent does not control discovery, persistence, retries, caching, reporting,
or application execution.

This release does not generate tailored CVs or cover letters, render the review Dashboard,
or submit applications.

## 2. Confirmed Product Decisions

- The workflow must be started inside Claude Code or Codex, and that agent session remains
  active until the workflow completes or reaches an explicit user-input checkpoint.
- No model provider abstraction, direct model API integration, extra API key, daemon, or
  separately deployed service is introduced.
- A thin Claude Code/Codex skill starts the workflow and services AI checkpoints. It does not
  decide the workflow order or keep business state.
- `jobsdb-assistant` owns the deterministic Python state machine.
- `ai-job-search` is used only for candidate onboarding and profile generation in this
  release.
- `career-ops` is the only job-scoring source. Its native scoring is retained without
  combining it with `ai-job-search`, adding custom weights, or converting it to a percentage.
- Both external projects remain unmodified forks pinned to exact commit SHAs.
- The integrations are installed from a main-repository lock manifest into ignored local
  directories; Git submodules and automatic upstream updates are excluded.
- Candidate profiles are never saved as active profiles until the user explicitly confirms
  them.
- Existing candidate profiles and integrations are reused on later runs unless the user
  explicitly requests an update or repair.

## 3. Approaches Considered

### 3.1 Selected: Python supervisor with controlled agent checkpoints

Python creates typed AI tasks, persists their state, and waits for the active Claude Code or
Codex skill to return schema-valid results. Python then resumes the state machine.

This keeps workflow control deterministic while using the authenticated agent session already
chosen by the user.

### 3.2 Rejected: Python model provider

The application could call OpenAI or Anthropic directly. This would support unattended CLI
execution but would introduce provider configuration, API credentials, and a second AI
execution path that the user does not require.

### 3.3 Rejected: skill-orchestrated workflow

The skill could independently call scripts and integrations in sequence. That would make
resume behavior and ordering dependent on agent judgment and duplicate state outside SQLite.
It is therefore unsuitable for the stable application and browser workflows.

## 4. Runtime Architecture

```text
Claude Code skill / Codex skill
  │
  │ starts one run and services typed AI checkpoints
  ▼
jobsdb-assistant Python supervisor
  ├── workflow state machine
  ├── integration lock validation
  ├── candidate profile repository
  ├── JobsDB discovery and immutable JD snapshots
  ├── evaluation task creation, validation, caching, and retry
  ├── run report
  └── SQLite system of record
        │
        ├── CandidateProfileAdapter checkpoint
        │     └── pinned ai-job-search fork capability
        │
        └── JobEvaluationAdapter checkpoint
              └── pinned career-ops fork capability
```

The adapters are contracts and task codecs, not services. They translate between
main-application domain models and the selected fork's instructions/templates. They never
write SQLite directly and cannot advance the workflow state.

## 5. First Run and Later Runs

### 5.1 First run

1. Create a persisted workflow run.
2. Read the integration lock manifest.
3. Install missing forks at the exact approved commits.
4. Validate repository identity, commit SHA, licence files, and required capability files.
5. Collect candidate input using an `ai-job-search` onboarding path:
   - local documents folder;
   - one CV; or
   - interactive interview.
6. Create a candidate-profile AI task.
7. Validate and display the proposed profile.
8. Wait for explicit user confirmation or revision feedback.
9. Save confirmed `CandidateProfile v1` and mark it active.
10. Discover JobsDB jobs and save immutable JD snapshots.
11. Evaluate all eligible snapshots not already covered by the evaluation cache.
12. Save successes and failures independently and produce a complete run report.

### 5.2 Later run

1. Create or resume a persisted workflow run.
2. Perform a read-only integration path and SHA check; do not install, pull, or update.
3. Load the current confirmed candidate profile without regenerating it.
4. Discover JobsDB jobs.
5. Reuse cached evaluations for unchanged jobs and evaluate only new or changed snapshots.
6. Produce a complete report for the current discovery set.

Candidate source-file changes may produce a warning, but they do not regenerate or replace the
profile automatically.

### 5.3 Explicit maintenance paths

- `profile update`: re-run onboarding, require confirmation, and create the next immutable
  profile version. Older versions remain available for audit and historical evaluations.
- `integration repair`: reinstall a missing or damaged integration at the currently locked
  SHA.
- `integration upgrade`: update a fork SHA only on a dedicated branch, then run adapter
  contract and golden-job regression tests before review and merge.

## 6. Python Workflow State Machine

The minimum persisted states are:

```text
CREATED
  → INTEGRATIONS_CHECKED
  → PROFILE_REQUIRED | PROFILE_READY
  → PROFILE_TASK_READY
  → PROFILE_REVIEW_REQUIRED
  → PROFILE_READY
  → DISCOVERY_RUNNING
  → EVALUATION_TASKS_READY
  → EVALUATING
  → REPORT_READY
  → COMPLETED
```

`WAITING_FOR_AGENT`, `WAITING_FOR_USER`, `PARTIALLY_COMPLETED`, and `FAILED` are explicit
conditions attached to a stage rather than implicit agent knowledge.

Only Python transitions workflow state. Every transition is validated and committed to SQLite
before the next side effect. Restarting the same run resumes from the last committed stage.

## 7. Integration Lock and Installation

The tracked lock manifest contains, for each fork:

- stable integration ID;
- exact approved public fork URL;
- exact commit SHA;
- licence identifier;
- required capability paths;
- adapter contract version.

Local clones live below ignored `integrations/`. Installation allows only the URLs and SHAs in
the manifest. It never accepts an arbitrary URL from an AI response, never tracks candidate
data in an integration repository, and never runs `git pull`.

Daily validation is read-only. A missing or mismatched checkout stops the affected stage with
an actionable repair message; it does not silently change versions.

## 8. Controlled AI Checkpoint Protocol

Each task is created by Python and contains:

- task ID and task type;
- schema and contract versions;
- integration ID and locked commit SHA;
- immutable input references and hashes;
- bounded instructions identifying the relevant fork capability;
- required output JSON Schema;
- attempt number and timestamps.

Private task payloads and results live under ignored runtime storage. SQLite stores the task
state, hashes, version references, validation errors, and audit timestamps.

The skill may:

1. ask Python for the next pending AI task;
2. read only the referenced input and pinned capability instructions;
3. use the current Claude Code or Codex model to complete that task;
4. return one JSON result for Python validation; and
5. ask Python to continue.

The skill may not select a different task type, change a locked SHA, write application state,
mark a task successful, or bypass validation.

Malformed output remains failed input, not workflow state. Python records the validation error
and may create a bounded retry using the same immutable inputs. A single job failure does not
discard successful evaluations for other jobs.

## 9. Candidate Profile

### 9.1 Input and privacy

Candidate documents are local runtime data and must remain ignored by Git. The profile task
receives file references and extracted text through private workspace files; source documents
are never copied into tracked fixtures, logs, reports, or CI artifacts.

### 9.2 Profile contents

The versioned contract contains at least:

- verified employment, project, education, skill, and metric facts;
- target roles;
- location, work-mode, salary, seniority, and other preferences;
- exclusions and hard constraints;
- writing style;
- source-document references and hashes;
- optional STAR examples;
- creation time, contract version, and active status.

Every asserted fact must retain source evidence or be marked as user-confirmed interview input.
Unsupported facts must not enter `verified_facts`.

### 9.3 Confirmation and versioning

AI output first becomes a profile proposal. The user can confirm it, reject it, or provide
revision feedback. Only a confirmed proposal becomes an active immutable profile version.

Updating a profile creates `v2`, `v3`, and so on; it never overwrites `v1`. Historical
evaluations retain their original `profile_version`.

## 10. Native Career-Ops Evaluation

`career-ops` is the sole scoring engine. The adapter retains its native:

- A–F evaluation dimensions;
- per-dimension assessment;
- 1.0–5.0 overall score;
- recommendation;
- strengths, gaps, risks, and supporting evidence.

The main application maps these outputs into typed fields and validates their ranges and
required evidence. It does not recalculate the score, add weights, merge another rating, or
convert the result to a percentage.

Each evaluation input binds one immutable JD snapshot to one confirmed candidate-profile
version and one locked evaluation-engine version. Evaluation can be processed as a bounded
batch, while every job retains its own task result and error state.

## 11. Caching and Incremental Evaluation

The evaluation cache identity includes:

- JD snapshot content hash;
- candidate-profile version and content hash;
- career-ops locked commit SHA;
- adapter contract version;
- evaluation prompt/rubric version.

An exact match reuses the prior result. A changed JD, confirmed profile version, engine SHA, or
rubric version creates a new evaluation. Cache reuse never changes the original evaluation
record.

The current run report covers all jobs in the current discovery set, whether their evaluation
was newly generated, reused, or failed.

## 12. Persistence

New migrations add repositories for:

- integration installation observations;
- workflow runs and stage transitions;
- candidate profile proposals and confirmed immutable versions;
- AI checkpoint tasks and attempts;
- immutable job evaluations;
- evaluation cache identities;
- run-to-job evaluation membership.

Domain data is written through main-application repositories only. Adapters and skills receive
no direct database-writing authority.

## 13. Report

`v0.3.0` produces a local CLI/text report; the interactive HTML Dashboard remains `v0.4.0`.
The report includes:

- run status and counts;
- active candidate-profile version;
- integration versions used;
- evaluated, cached, and failed counts;
- all current jobs ordered by native overall score, with ties handled deterministically;
- job title, company, application type, native dimensions, recommendation, strengths, gaps,
  risks, and concise evidence;
- validation or execution reason for failed evaluations.

Private candidate facts and full JD bodies are not printed by default.

## 14. Failure and Recovery Rules

- Missing active profile: enter `PROFILE_REQUIRED`; do not evaluate.
- Unconfirmed profile proposal: remain `WAITING_FOR_USER`.
- Missing/mismatched integration: stop the affected stage and offer explicit repair.
- Invalid AI result: retain the attempt and validation error, then allow bounded retry.
- Individual evaluation failure: continue the batch and mark the job failed in the report.
- Agent session interruption: retain pending tasks and resume them in a later CC/Codex session.
- Discovery failure: preserve the previous completed run; never represent stale data as a new
  successful discovery.
- No workflow path in this release invokes Quick Apply submission.

## 15. Security and Public-Repository Rules

- Candidate documents, profile payloads, JD task payloads, AI outputs, reports, SQLite files,
  integration checkouts, and agent runtime settings remain ignored.
- Tracked examples use synthetic people, employers, job descriptions, URLs, and hashes.
- Logs contain task IDs and error categories, not raw candidate facts or document contents.
- The installer executes no integration-provided setup script automatically.
- Fork attribution and licences are preserved locally and documented publicly.
- Existing privacy guard and secret scanning remain mandatory.
- Existing untracked probe scripts remain untouched.

## 16. Testing and TDD

Implementation follows strict RED–GREEN–REFACTOR with committed RED and GREEN checkpoints.

Required coverage includes:

- unit tests for state transitions, profile confirmation/versioning, schemas, native score
  validation, cache keys, and retry rules;
- integration tests for migrations, repositories, lock validation, task hand-off, resume, and
  partial batch persistence;
- contract fixtures for both Claude Code and Codex using synthetic inputs and outputs;
- golden candidate-profile and career-ops evaluation fixtures locked to integration commits;
- regression coverage for existing discovery and application behavior;
- at least 80% repository coverage and at least 90% for new or materially changed application
  modules.

Automated tests never require a live model, real candidate documents, real JobsDB data, or
network access. One manual acceptance run inside Claude Code and one inside Codex verify the
actual checkpoint workflow before release.

## 17. Acceptance Criteria

The release is complete when:

1. a first run installs the two locked integrations and creates a candidate profile proposal;
2. no profile becomes active before explicit user confirmation;
3. the first confirmed profile is stored as immutable `v1`;
4. a later normal run reuses the installed integrations and active profile without
   regeneration;
5. an explicit profile update creates `v2` without modifying `v1`;
6. current JobsDB snapshots are evaluated only by native `career-ops` scoring;
7. exact cache matches are reused and changed inputs create new evaluations;
8. partial failures are reported without losing successful results;
9. interrupted workflows resume from persisted Python state;
10. the current discovery set produces a complete local report;
11. Claude Code and Codex can each service the same typed checkpoint protocol;
12. existing JobsDB discovery and application tests remain green; and
13. privacy and secret guards pass with no personal or runtime data tracked.

## 18. Explicitly Deferred

- HTML review Dashboard and checkbox selection (`v0.4.0`);
- tailored English CV and 100–300-word English cover letter (`v0.5.0`);
- material approval and regeneration (`v0.6.0`);
- Quick Apply automatic execution and Apply detail-page action (`v0.7.0`);
- unattended model APIs, scheduled runs, deployment, and multi-user operation;
- automatic fork updates;
- scoring fusion or custom weighting.
