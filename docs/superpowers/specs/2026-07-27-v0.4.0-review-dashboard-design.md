# v0.4.0 Review Dashboard Design

**Date:** 2026-07-27
**Status:** Approved for implementation planning
**Project:** `jobsdb-assistant`

## 1. Purpose

v0.4.0 adds a local review Dashboard to the existing Python application. It
lets a candidate inspect discovered JobsDB roles, understand the native
Career Ops A-F evaluation, select roles for later tailored materials, and
optionally submit one Quick Apply role immediately with the CV already
configured as the JobsDB default and without a cover letter.

The Dashboard is a presentation and control layer over the existing stable
Python workflows. It does not replace discovery, candidate profiling,
Career Ops evaluation, or the JobsDB application state machine.

## 2. Product Scope

### 2.1 Included

- Run a local-only FastAPI service from the main `jobsdb-assistant` CLI.
- Render a server-side Jinja2 Dashboard with small Vanilla JavaScript
  enhancements.
- Default to current, scored JobsDB roles.
- Allow the user to include unscored roles, which display as
  `Pending evaluation`.
- Filter by score, application type, selection status, title, and company.
- Show title, company, location, application type, overall score, A-F
  dimensions, recommendation, strengths, gaps, risks, and evidence.
- Expand a job to show its full JD and native scoring trace.
- Show evaluation provenance: profile version, JD snapshot, evaluation time,
  Career Ops commit, prompt/contract version, and cache information when
  available.
- Show the relevant candidate Profile summary beside the evaluation for
  human comparison.
- Select or deselect jobs immediately, with durable SQLite persistence.
- Mark selected jobs as `waiting_for_materials`.
- Open the original JobsDB job in a new browser tab.
- For a single Quick Apply job, explicitly confirm and run the existing
  browser application flow using the JobsDB default CV and no cover letter.
- For an Apply job, open the JobsDB details page for manual continuation.
- Show the future tailored-material/application actions without implementing
  those later workflows.

### 2.2 Excluded

- Candidate Profile gap interviews or Career Ops profile enrichment.
- Tailored CV generation.
- Cover-letter generation.
- Material review, regeneration, or approval.
- Batch application from the Dashboard.
- Automated application for JobsDB Apply roles.
- Scheduled or unattended execution.
- Public hosting, LAN binding, remote access, authentication, or multiple
  Dashboard users.
- Independent re-scoring or changes to Career Ops scoring rules.
- Source changes in either pinned fork.
- JD-change invalidation for a previously selected job.

## 3. User Flow

### 3.1 Start and review

```text
CC/Codex starts the jobsdb-assistant skill
  -> the skill starts the stable Python CLI
  -> the CLI validates the environment and database
  -> FastAPI binds to 127.0.0.1
  -> /health becomes ready
  -> the local browser opens
  -> the Dashboard reads current jobs and evaluations from SQLite
```

The default view contains only evaluated roles. The user can switch to all
roles, inspect the scoring process, filter the set, and open the source role.

### 3.2 Select for later materials

```text
User checks a job
  -> Dashboard writes the selection immediately
  -> status becomes waiting_for_materials
  -> selected count changes
  -> refresh restores the same state
```

Unchecking the role removes the current selection. A selection is bound to
the stable JobsDB job ID. v0.4.0 does not model JD changes.

### 3.3 Direct Quick Apply

```text
User clicks "Direct apply with default CV"
  -> confirmation states:
       use the current JobsDB default CV
       do not tailor or upload a CV
       do not include a cover letter
       submission cannot be withdrawn by this system
  -> user confirms
  -> backend validates job ID, type, history, and rate limits
  -> existing Quick Apply browser state machine runs
  -> result is persisted and reported
```

This path is independent of job selection and must not create a material
task. Only one browser application may execute at a time.

### 3.4 Apply role

An Apply role is never passed to the automated application flow. Its action
opens the JobsDB details page so the user can find and follow the employer
site link manually.

## 4. Architecture

The Dashboard remains inside the main repository and process:

```text
CC / Codex skill
       |
       v
jobsdb-assistant Python CLI
       |
       +-- FastAPI on 127.0.0.1
       +-- Jinja2 HTML
       +-- Vanilla JS and CSS
       +-- existing SQLite database
       +-- existing discovery/evaluation repositories
       +-- existing Quick Apply orchestrator/state machine
```

Proposed module ownership:

```text
src/dashboard/
  app.py                 FastAPI construction and lifecycle
  routes.py              HTML and JSON routes
  query_service.py       dashboard read-model aggregation
  application_service.py guarded single-job Quick Apply execution
  schemas.py             HTTP and read-model contracts
  templates/index.html   local Dashboard document
  static/dashboard.js    filtering, expansion, selection, polling
  static/dashboard.css   desktop-first local-tool styling

src/storage/
  selection_repository.py
```

The Dashboard depends on application services and repository protocols. HTTP
routes must not contain JobsDB browser automation or direct SQLite queries.

## 5. Persistence

### 5.1 Job selections

Add `job_selections`:

| Column | Meaning |
|---|---|
| `job_id` | Stable JobsDB job ID and primary key |
| `status` | `waiting_for_materials` in v0.4.0 |
| `selected_at` | Initial selection timestamp |
| `updated_at` | Latest update timestamp |

Only selected jobs have rows. Selecting inserts idempotently; deselecting
deletes. The table does not duplicate the JD, company, evaluation, or Profile.
The repository rejects unknown job IDs so orphan selections cannot be
created.

### 5.2 Application execution

Existing application history remains the source of truth for application
outcomes. If a durable task record is required to recover UI state after a
refresh, it must contain only execution identity and status, not credentials,
cookies, CV contents, or duplicated JD data.

The state vocabulary is:

```text
ready
applying
submitted
needs_attention
failed
skipped_already_applied
```

The implementation plan must prefer an existing compatible execution/history
record before introducing another table.

## 6. Dashboard Read Model

`DashboardQueryService` combines:

```text
current active job and current snapshot
  + latest evaluation for the active Profile version
  + current selection
  + existing application history/status
  = DashboardJob
```

The default ordering is overall score descending, then company, title, and
job ID for deterministic results. Unscored jobs appear only when requested.

The service supports:

- evaluated-only versus all;
- overall score/grade;
- Quick Apply versus Apply;
- selected versus unselected;
- case-insensitive title/company search.

Filter state is represented in URL query parameters so a refresh preserves
the current view.

## 7. Scoring Visualization

### 7.1 Truthful source boundary

The persisted `JobEvaluation` already contains:

- `overall_score`;
- `recommendation`;
- `strengths`, `gaps`, `risks`, and overall `evidence`;
- ordered native A-F dimensions;
- each dimension's title, optional score, findings, and evidence;
- profile version/hash;
- JD snapshot/hash;
- engine version/commit;
- prompt version;
- evaluation timestamp.

The Dashboard displays these values without recalculating or interpreting a
new score.

The current contract does not provide a structured, per-Profile-requirement
verdict such as `met`, `not met`, or `unknown`. The Dashboard therefore must
not manufacture those verdicts. It may display a Profile summary for human
comparison and show an explicit message when no independent structured
verdict exists.

### 7.2 Card summary

Each evaluated job card contains:

```text
Title and company                       overall score / 5
A n.n  B n.n  C n.n  D n.n  E n.n  F n.n
recommendation
short strengths, gaps, and risks
application type and current selection/application status
```

Missing dimension scores display `—`, not zero.

### 7.3 Expanded scoring trace

The expanded view shows, for each A-F block:

- the original Career Ops dimension code and title;
- the persisted score;
- all persisted findings;
- all persisted evidence.

It then shows strengths, gaps, risks, overall evidence, evaluation provenance,
the Profile summary, and the full current JD. If a field is absent, the UI
states that structured information is unavailable rather than inferring it.

### 7.4 Batch summary

The page header shows:

- total current roles;
- evaluated and pending counts;
- A-F/score distribution where the existing score representation supports
  it;
- selected count;
- common persisted strengths, gaps, or risks only when they can be summarized
  deterministically without new AI scoring.

Clicking a score/grade bucket filters the list.

## 8. Interface

Desktop-first low-fidelity structure:

```text
+------------------------------------------------------------------+
| JobsDB Assistant                         N jobs selected          |
| search context                      Refresh | Open JobsDB search  |
+------------------------------------------------------------------+
| Show | Score | Apply type | Selection | title/company search     |
+------------------------------------------------------------------+
| [ ] Job title                              score | Quick Apply     |
|     company and location                                        |
|     recommendation, strengths, gaps, risks                      |
|     [Scoring details] [Open JobsDB] [Direct apply default CV]    |
+------------------------------------------------------------------+
| [x] Job title                              score | Apply           |
|     status: waiting for materials                               |
|     [Scoring details] [Open job and apply manually]              |
+------------------------------------------------------------------+
```

Quick Apply actions:

- select/deselect for future materials;
- direct apply with default CV;
- open JobsDB.

Apply actions:

- select/deselect for future materials;
- open the job and apply manually.

The later tailored-material action may be visible as disabled and clearly
labelled as a later version. Apply must never display an enabled automatic
application control.

## 9. HTTP Interface

Minimum routes:

```text
GET    /                                  Dashboard HTML
GET    /api/jobs                          filtered read model
PUT    /api/selections/{job_id}           select
DELETE /api/selections/{job_id}           deselect
POST   /api/jobs/{job_id}/quick-apply     guarded direct application
GET    /api/applications/{task_id}        execution status polling
GET    /health                            readiness
```

The direct-application request explicitly declares:

```json
{
  "resume_mode": "jobsdb_default",
  "cover_letter_mode": "none"
}
```

No arbitrary URL, file path, CV payload, or cover-letter text is accepted.

## 10. Quick Apply Guardrails

- Require a visible confirmation before the request.
- Resolve the job and original URL from SQLite using the supplied job ID.
- Reject any non-Quick Apply role.
- Re-check application history before browser activity.
- Preserve existing scheduler frequency and minimum-interval controls.
- Use the existing browser profile and Quick Apply state machine.
- Always select `Don't include a cover letter`.
- Use the CV currently configured as the JobsDB default.
- Do not call CV tailoring, cover-letter generation, or material-task code.
- Make repeated requests idempotent.
- Permit only one active browser application for the local profile.
- Disable other direct-application controls while a job is executing.
- Persist/report success, failure, skip, and human-attention outcomes through
  the existing application reporting path.
- Treat login expiry, CAPTCHA, or a complex form as human-attention states;
  do not bypass site verification.
- A disconnected HTTP client or refreshed page must not trigger a duplicate
  submission.

## 11. Local Security and Privacy

- Bind only to `127.0.0.1`; do not expose LAN or public interfaces.
- Do not enable remote CORS.
- Do not display credentials, cookies, environment values, browser-profile
  contents, or full candidate source files.
- Do not accept arbitrary filesystem paths through HTTP.
- Do not log CV content, credentials, cookies, or environment values.
- Use database records as the authority for job URLs and types.
- Preserve existing ignored local data and privacy checks.
- Do not modify pinned fork repositories.

## 12. Environment and CLI

Use one recreated project `.venv`, not a separate Dashboard environment:

```bash
uv venv
uv sync --extra dev --extra dashboard
uv pip list
```

The `dashboard` optional dependency group contains pinned compatible versions
of FastAPI, Uvicorn, and Jinja2. The lock file makes installation reproducible
on another supported computer.

CLI:

```bash
uv run python -m src.main dashboard start
uv run python -m src.main dashboard start --port 8765
uv run python -m src.main dashboard start --no-browser
uv run python -m src.main dashboard doctor
```

Start behavior:

```text
validate runtime and dependencies
  -> validate/migrate SQLite
  -> check requested port
  -> bind 127.0.0.1
  -> wait for /health
  -> open the local browser unless disabled
  -> remain active until interrupted
```

A busy port is reported rather than silently changed. Browser-open failure
does not stop a healthy server. `Ctrl+C` performs a normal shutdown.

`doctor` reports Python/dependency readiness, database access and schema,
current job/Profile/evaluation counts, and port availability without printing
private values.

## 13. Failure Handling

- Query failure: render an explicit error state and retry action.
- Selection failure: restore the checkbox and display the reason.
- Unknown job: return `404`; do not create a selection or task.
- Duplicate selection/application request: return the current idempotent
  state.
- Invalid filter or request: return `422`.
- Unscored job: display `Pending evaluation`.
- Missing scoring field: display an unavailable message.
- Missing JobsDB URL: disable the open action.
- Apply role sent to Quick Apply: reject it without browser activity.
- Another application running: reject or report busy without queueing a
  surprise submission.
- Database migration failure: do not start; preserve the original database.
- Login/CAPTCHA/complex form: report `needs_attention`.
- Application failure: show phase, reason, and existing screenshot reference
  when available.

## 14. TDD Strategy

Every increment follows RED, GREEN, REFACTOR. Product code is written only
after its focused test fails for the expected reason.

### 14.1 Repository tests

- select, idempotent re-select, and deselect;
- reject unknown job IDs;
- restore selections after repository recreation;
- migrate without modifying existing job, evaluation, or application data.

### 14.2 Query-service tests

- evaluated-only default and explicit all-jobs mode;
- `Pending evaluation` for an unscored job;
- latest current evaluation for the active Profile;
- correct A-F, evidence, application type, selection, and history data;
- deterministic ordering and all filters;
- no invented scoring verdicts or evidence.

### 14.3 API tests

- health/readiness;
- stable job read model;
- selection lifecycle and error contracts;
- Quick Apply request schema and job/type validation;
- idempotency, history check, rate limits, and single-execution lock;
- Apply rejection without browser activity;
- no private values in responses.

### 14.4 Browser tests

- page load and evaluated-only default;
- all-jobs toggle and pending label;
- filters and URL persistence;
- A-F trace, evidence, Profile summary, provenance, and full JD expansion;
- immediate selection count and refresh persistence;
- correct source URL opening;
- distinct Quick Apply and Apply controls;
- disabled later-version controls;
- confirmation before direct application;
- execution progress and refresh recovery;
- UI rollback on selection failure;
- no parallel direct application.

### 14.5 CLI and installation tests

- clean `.venv` installation with dev and Dashboard extras;
- `dashboard doctor`;
- `dashboard start --no-browser`;
- fixed local binding and requested-port failure;
- clean interrupt shutdown;
- README commands run as written.

## 16. Manual Acceptance

```text
start the Dashboard
  -> inspect evaluated jobs
  -> expand one native A-F scoring trace and its evidence
  -> verify Profile/JD/Career Ops provenance
  -> include all jobs and observe Pending evaluation
  -> filter Quick Apply roles
  -> select a job and refresh to confirm persistence
  -> deselect it
  -> open a JobsDB source job
  -> confirm an Apply role only opens for manual handling
  -> confirm one Quick Apply direct application
  -> verify default CV and no-cover-letter mode
  -> verify application history/reporting
  -> verify no material task was created
```

## 17. Version Boundary

v0.4.0 ends with a local review and control surface. It can persist jobs chosen
for later materials and can invoke the already-existing single-job Quick
Apply path in a deliberately constrained default-CV/no-cover-letter mode.

Tailored materials, material approval, regeneration, and their eventual
application actions remain later-version responsibilities.
