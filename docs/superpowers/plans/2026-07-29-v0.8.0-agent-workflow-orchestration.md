# v0.8.0 Agent Workflow Orchestration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build one versioned Python Agent-work protocol so a single Claude Code or Codex Skill invocation continuously services Dashboard-triggered profile, scoring, translation, and material work without guessing IDs or rereading application source.

**Architecture:** Add durable `agent_sessions` and `agent_work_items` tables, expose them through a focused repository and coordinator, and present a six-command `jobsdb-assistant agent` CLI. Existing profile, evaluation, material, discovery, and application services remain authoritative; the coordinator adapts their pending work into one opaque `work_id` queue and dispatches validated results back to the existing services.

**Tech Stack:** Python 3.11+, Typer, Pydantic v2, SQLite, FastAPI Dashboard, pytest, Playwright, uv, ruff.

## Global Constraints

- Python and SQLite are the only workflow-state and identifier authority.
- The Agent sees one opaque `work_id`; it never constructs or parses internal IDs.
- The Agent reads one task and only envelope-declared capability/context paths.
- AI Job Search and Career Ops remain pinned, read-only integration checkouts.
- Dashboard discovery automatically queues scoring; Dashboard material requests automatically queue material work.
- `idle` is not completion: the foreground Agent keeps listening until explicit stop, unrecoverable failure, or user cancellation.
- Candidate confirmation, material review, Quick Apply final confirmation, login, and CAPTCHA remain human gates.
- No provider API, cloud daemon, external Apply automation, or automatic human approval.
- Runtime data remains local and ignored by Git.
- Implement every behavior red-green-refactor with focused tests before production code.

```python
"""Stable contracts between Python workflow state and an active AI Agent."""

from datetime import datetime
from enum import Enum
from pathlib import Path
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, model_validator

PROTOCOL_VERSION = 1


class AgentWorkKind(str, Enum):
    CANDIDATE_QUESTIONS = "candidate_questions"
    CANDIDATE_PROPOSAL = "candidate_proposal"
    JOB_EVALUATION = "job_evaluation"
    APPLICATION_MATERIAL = "application_material"
    HUMAN_RESPONSE = "human_response"


class AgentWorkStatus(str, Enum):
    QUEUED = "queued"
    CLAIMED = "claimed"
    HUMAN_REQUIRED = "human_required"
    COMPLETED = "completed"
    FAILED = "failed"
    IDLE = "idle"
    STOPPED = "stopped"


class AgentSessionStatus(str, Enum):
    ACTIVE = "active"
    STOPPED = "stopped"
    FAILED = "failed"


class AgentWorkEnvelope(BaseModel):
    model_config = ConfigDict(frozen=True)

    protocol_version: Literal[1] = PROTOCOL_VERSION
    session: str = Field(min_length=1)
    state: Literal[AgentWorkStatus.CLAIMED] = AgentWorkStatus.CLAIMED
    work_id: str = Field(pattern=r"^work-[a-f0-9]{24}$")
    kind: AgentWorkKind
    task_path: Path
    result_path: Path
    capability_paths: tuple[Path, ...]
    attempt: int = Field(ge=1)
    lease_expires_at: datetime


class AgentHumanGate(BaseModel):
    model_config = ConfigDict(frozen=True)

    protocol_version: Literal[1] = PROTOCOL_VERSION
    session: str = Field(min_length=1)
    state: Literal[AgentWorkStatus.HUMAN_REQUIRED] = (
        AgentWorkStatus.HUMAN_REQUIRED
    )
    work_id: str = Field(pattern=r"^work-[a-f0-9]{24}$")
    prompt_path: Path
    response_path: Path


class AgentNextResult(BaseModel):
    model_config = ConfigDict(frozen=True)

    protocol_version: Literal[1] = PROTOCOL_VERSION
    state: AgentWorkStatus
    work: AgentWorkEnvelope | AgentHumanGate | None = None
    message: str | None = None

    @model_validator(mode="after")
    def validate_state_payload(self) -> "AgentNextResult":
        expects_work = self.state in {
            AgentWorkStatus.CLAIMED,
            AgentWorkStatus.HUMAN_REQUIRED,
        }
        if expects_work != (self.work is not None):
            raise ValueError("work-bearing state and envelope must match")
        if self.work is not None and self.work.state is not self.state:
            raise ValueError("result state and work state must match")
        return self


class AgentSubmission(BaseModel):
    model_config = ConfigDict(frozen=True)

    protocol_version: Literal[1] = PROTOCOL_VERSION
    session: str = Field(min_length=1)
    work_id: str = Field(pattern=r"^work-[a-f0-9]{24}$")
    result_path: Path
```

- [ ] **Step 4: Implement transactional repository behavior**

Use `uuid.uuid4().hex[:24]` only inside the repository. `claim_next()` must
run one transaction that:

1. moves expired `claimed` rows back to `queued`;
2. selects the oldest queued row;
3. updates it to `claimed`, binds the session, increments `attempt`, and sets
   `lease_expires_at`;
4. returns the persisted row.

`complete()` accepts an already completed row only when its `result_hash`
matches; a different hash raises `ValueError`. A non-owner session cannot
complete or fail an active lease.

- [ ] **Step 3: Implement source synchronization**

Define:

```python
class AgentWorkSources(Protocol):
    def current_profile_task_ids(self) -> tuple[str, ...]: ...
    def current_evaluation_task_ids(self) -> tuple[str, ...]: ...
    def pending_material_task_ids(self) -> tuple[str, ...]: ...


class AgentWorkDispatcher(Protocol):
    def submit_profile(self, task_id: str, payload: dict) -> object: ...
    def submit_evaluation(self, task_id: str, payload: dict) -> object: ...
    def submit_material(self, task_id: str, payload: dict) -> object: ...
```

`sync_pending()` maps each source to a stable internal key:

```text
profile:<task-id>
evaluation:<task-id>
material:<task-id>
```

It reads the existing task JSON only to obtain declared `capability_paths` and
result location. It does not expose the internal key in the envelope.

Profile orchestration stores `run_id`, source paths, proposal identity, and
question dimensions in private work metadata. When a candidate-questions
submission returns interview questions, the coordinator completes that AI
work and creates one `human_response` work item. Submitting the user's
dimension-keyed answers dispatches to existing `submit_profile_answers()` and
queues the resulting candidate-proposal task. A proposal submission creates a
profile-confirmation human item; explicit approval dispatches to
`confirm_profile()`. The Skill never carries a proposal ID between commands.

- [ ] **Step 4: Implement next, submit, fail, and stop**

`next()` performs `sync_pending()`, claims one item, and returns an
`AgentNextResult`. With no item, it waits using a short injected sleeper in
production and a no-op sleeper in tests until `wait_seconds` expires, then
returns `idle`.

`submit()` must:

1. load the claimed row by opaque `work_id` and owner session;
2. require the supplied result path to equal the persisted result path;
3. calculate SHA-256 before dispatch;
4. dispatch by the persisted `kind`;
5. mark the item completed only after existing Python validation succeeds;
6. call `sync_pending()` because profile submission may create its next task;
7. leave validation failures recoverable and record the exact error.

- [ ] **Step 5: Construct production dependencies**

`build_agent_work_coordinator(project_root: Path | None = None)` must reuse the
same database, manifest, checkpoint root, active profile workflow, evaluation
progress store, and material repository as the existing application runtime.
It must not create a second database path or integration manager.
