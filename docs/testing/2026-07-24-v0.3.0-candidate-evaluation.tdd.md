The user later constrained execution to the minimum v0.3 outcome. Existing
infrastructure was retained, while implementation stopped at candidate
onboarding, native evaluation, exact caching, a safe report, and shared agent
entrypoints. Dashboard, tailored materials, approval, and application execution
remain deferred.

## User Journeys

1. As a first-time user, I can start inside Claude Code or Codex, build an
   evidence-backed candidate profile, review it, and explicitly confirm v1.
2. As a repeat user, I reuse the active profile and fixed integration revisions
   without regenerating or updating them.
3. As a job seeker, I can evaluate current JobsDB JDs using only native
   career-ops A–F and 1.0–5.0 scoring.
4. As a repeat user, unchanged JD/profile/engine inputs reuse cached results.
5. As a privacy-conscious user, candidate documents, JDs, and AI payloads stay
   in ignored local storage.
6. As a reviewer, I receive a score-sorted report without full JDs or raw
   candidate facts.

## Private Acceptance Boundary

No live candidate profile or real job-evaluation payload is committed. The
automated acceptance path uses synthetic data. A real Claude Code/Codex run
requires the user's private documents, JobsDB login, and explicit profile
approval; it is intentionally performed through ignored `workspace/` and
`data/` paths rather than recorded in Git.
